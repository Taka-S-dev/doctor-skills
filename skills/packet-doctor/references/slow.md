# 遅い

対象: 応答が遅い、転送が遅い、もたつく、たまにタイムアウトする。

遅さは「ネットワーク」「サーバーの処理」「受信側の処理」「送信の仕方」のどれかに分ける。最初に、時間がどの区間に使われているかを数字で示す。

## 時間の内訳を読む

`summary.measurements` と `query --conn` の `stats` を見る。

| 指標 | 読み方 |
|---|---|
| `rtt` | ネットワークの往復時間の目安。ACKが基準なので受信側の処理時間は含みにくい |
| `application_turnaround` | 要求から応答までの間隔。RTTより大幅に長ければサーバー側の時間が候補 |
| `handshake_split` | SYN→SYN/ACKが長ければサーバー方向、SYN/ACK→ACKが長ければクライアント方向に遅延がある |
| `retransmissions` / `rto_like_retransmissions` | RTO型（200 ms以上あけた再送）は1回で体感の遅延になる |
| `zero_window_ms` | 受信側が受け取れなかった時間の合計 |
| `max_idle` | 最も長い無通信区間と、その前後のパケット |

## 所見から切り分ける

| 観測 | 候補 | 決め手になる確認 |
|---|---|---|
| ACKはすぐ返るが、応答データが遅い（`app_response_slow`） | サーバーのアプリ・バックエンド | サーバーの処理ログと同じ時刻で比較 |
| 再送がある（`tcp_repeated_data`） | 経路ロス | 両端取得で区間を特定、NIC/スイッチのエラーカウンタ |
| 大きなセグメントだけ再送（`tcp_large_segment_loss`） | MTUブラックホール | DF付きping、VPN/トンネル区間の確認 |
| Zero Window（`tcp_zero_window`） | 受信アプリの処理停滞 | 受信側のCPU・タスク状態 |
| 約40 ms / 200 msの遅延ACKが反復（`delayed_ack_pattern`） | NagleとDelayed ACK | 小さな書き込みの分割、TCP_NODELAY |
| 仕様の応答時間超過（`protocol_response_late`） | 機器の処理、経路の再送 | 同じ時間帯の再送の有無、機器ログ |

## 誤りやすい点

- 取得位置で内訳は変わる。サーバー近くで取ると応答間隔はほぼ処理時間だが、クライアント近くで取ると往復時間を含む。`observation_position` は推定なので利用者の申告を優先する。
- 再送が0でも取得の外で起きていることがある。送信元から取得点までに失われた初回の送信は見えない。`capture_gaps` があれば再送数は下限として読む。
- `rtt` の最大値には遅延ACKなど受信側の待ちが混ざる。ネットワークの遅延は最小値と中央値で見る。
- 送信端末上の取得は、TSOでMTUより大きなセグメントに見える（`offload_on_sender`）。
- 平均だけで判断しない。最大値の時刻と、症状が出た時刻を合わせる。
- 正常時の記録があれば `compare` で差を確かめる。ただし条件の同等性は別途確認する。
