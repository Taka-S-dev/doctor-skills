# 復帰しない・再接続が遅い

対象: 切断後の復帰に時間がかかる、再接続しない。

復帰までの時間を区間に分け、どの区間に時間があるかを示す。観測できない区間は「不明」と書く。

| 区間 | 観測手段 | パケットでわかること |
|---|---|---|
| 機器が異常を検知するまで | 機器ログ | 確定できない |
| 検知後、再接続を始めるまで | ログとpcapの照合 | 次のSYNの時刻のみ |
| TCP接続の成立まで | `tcp_handshake_ms` | 計測できる |
| 成立後、アプリ通信の再開まで | 仕様ルール、`app_turnaround_max_ms` | 仕様があれば計測できる |
| 期待する動作に戻るまで | 機器ログ、操作結果 | 確定できない |

## 計測の読み方

- `observed_gap_before_next_connect_ms`: 終了イベント（FIN/RST）から次のSYNまで。
- `observed_silence_before_next_connect_ms`: 終了イベントなしで、最後の通信から次のSYNまで。電源断やケーブル抜けはこちらになる。

どちらも観測上の間隔であり、機器内部のリトライ時間と同じではない。

## 所見から切り分ける

| 観測 | 候補 | 決め手になる確認 |
|---|---|---|
| 間隔がほぼ一定（`reconnect_interval_regular`） | アプリの固定リトライ | 設定値と機器ログの再接続開始時刻 |
| SYNはすぐ出るが成立しない | 相手の復帰待ち、FWの状態 | 相手の待受、成立までの再試行回数 |
| 成立は早いが仕様の応答が遅い | 機器の初期化処理 | 成立後の最初の要求と応答 |
| 同じ送信元ポートでSYNが反復 | OSの再送 | 別の接続試行と区別する |

## 確認の順番

1. `reconnect_candidates` の `ambiguous` を確認する。並行接続があれば対応付けを利用者に確認する。
2. 取得の欠落（`capture_gaps`）を確認する。欠落があれば間隔の信頼性が下がる。
3. 機器ログの切断検知時刻と再接続開始時刻を `add-evidence` で登録する。
4. 処理開始が遅ければリトライ設定やタスク待ち、すぐ開始していれば送信処理や観測位置を調べる。

機器内部の時計とPCの時計はずれている。ログと照合するときは `log-match --clock-offset-ms` で補正値を明示し、補正の根拠と不確かさも説明する。
