# 切れる・間欠的に起きる

対象: 途中で切断される、ときどき止まる、放置すると切れる。

最初に「誰が終わらせたか」を確認する。`tcp_reset` の `details.sender` と、FIN/RSTの方向を見る。

## 終わり方で切り分ける

| 観測 | 候補 | 決め手になる確認 |
|---|---|---|
| 相手からRST（`tcp_reset`） | 相手アプリの中断、FW、相手の再起動 | 相手のログ。TTLの比較（`tcp_rst_ttl_anomaly`）、両端取得 |
| 相手の通常と違うTTLのRST | 経路上の機器が生成 | FW/IPSのログ。両端取得で片側だけに見えるなら確定に近づく |
| 自分側からRST（`sender_gave_up_after_retransmissions`） | 応答がないため送信側が打ち切った | 原因は打ち切りの前にある。相手の応答が消えた時刻を調べる |
| 再送を続けて応答が途絶（`tcp_unanswered_tail`） | 相手の停止、ケーブル断、経路断 | 相手の電源・リンク、スイッチのログ |
| FINで終了 | 正常終了、アプリの判断 | FINは半閉鎖の場合がある。アプリのログ |
| 応答のない再送の後に自分側がFINまたはRST | 送信側が打ち切った。終わらせた側は原因ではない | 応答が消えた時刻より前を調べる |
| 無通信の直後に失敗（`tcp_failure_after_idle`） | FW/NATのセッション切れ、アプリのアイドル切断 | タイムアウト設定と `idle_ms` の比較、ハートビート間隔 |

## 間欠的な症状の進め方

1. 発生時刻を `--when` で渡し、`incident_outside_capture` が出ないことを確認する。
2. 発生していない時間の記録があれば `compare` で差を確かめる。
3. 長時間の取得は `live` または分割取得にする。リングバッファは発生時刻の記録が消えないよう、停止条件を合わせる。
4. 間隔が一定なら定期処理やタイムアウトを疑う。発生時刻の間隔を計算して示す。
5. L2の揺れ（`arp_duplicate_ip`）を確認する。IP重複は間欠症状の典型である。

応答が途絶えている間も、相手のARPなど非TCPの通信が届いていないかをtsharkで確認する（`query --conn` にはTCPしか出ない）。届いていれば相手は動いており、TCPだけが処理されていない方向を調べる。

`tcp_failure_after_idle` は30秒以上の無通信の直後に失敗したときに出る。短い無通信で出ないことは、タイムアウトの可能性を否定しない。

## 誤りやすい点

- 最後のパケットの時刻は切断時刻ではない。
- RSTを送った側が原因とは限らない。応答がなくて打ち切った側かもしれない。
- 片側の取得だけでは「途中の機器が切った」と確定できない。
